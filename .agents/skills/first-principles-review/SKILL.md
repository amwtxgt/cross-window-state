# 第一性原理 + 对抗式代码审查

对**审查范围内的代码**做一次彻底的再审视。目标不是挑刺，而是在**保证功能、接口、行为完全一致**的前提下，让代码更简单、更安全、更易维护。

## 修改优先级（核心原则）

靠前的优先，判断时从上往下走：

1. **删除** — 能删的代码最安全。死代码、只用一次的抽象、纯转发的 wrapper、无人传非默认值的配置项、不可达分支。
2. **简化** — 同样结果用更直接的写法。标准库 API > 手写循环；不可变操作 > 手动拷贝。优先查阅 `vue-component` 里的 ES2015–ES2025 速查表。
3. **可读** — 命名能读出意图、一个函数只做一件事、层级不越级混用。
4. **保持** — 当前实现已足够好时不改，明确说明原因。**不为了修改而修改。**

> **硬约束：** 任何修改不得改变对外接口、返回结构、副作用顺序、事件触发时机、渲染产物。这是不可妥协的底线。

## 工作流

### Step 0 — 确定审查范围

范围按实际情况确定，优先级从高到低：

- **用户指定了范围**（文件/目录/符号/commit/PR 等）：以用户指定的范围为审查对象，不自行收窄或扩散
- **用户未指定（默认）**：审未提交的改动或刚完成的代码——调用 GitNexus `detect_changes()` 拿到本次改动的符号与执行流，作为审查对象
- 范围外的既有问题：**只提示，不改动**（surgical changes，与 `karpathy-guidelines` 一致）

### Step 1 — 改动前必做：影响分析

对任何准备修改的符号（函数/类/方法/组件），**先**运行 GitNexus 影响分析：

```
impact({ target: "符号名", direction: "upstream" })
```

按风险等级处置：

| 风险 | 判据 | 动作 |
| --- | --- | --- |
| LOW | 0–3 个消费者 | 直接改 |
| MEDIUM | 4–9 个消费者或有 mismatch | 改完重点回归 |
| **HIGH/CRITICAL** | 10+ 个消费者，或 mismatch 伴随多消费者 | **必须先告知用户风险，等确认再动** |

`.vue` 组件改动还需遵守 `vue-component` 规范；注释风格见 `code-comments`。

### Step 2 — 第一性原理审查（七维度）

逐维度过，**用问题驱动**，不要泛泛地「检查」：

| 维度 | 关键追问 |
| --- | --- |
| ① 冗余/过度设计 | 这个抽象只用了一次？这个配置项没人传非默认值？这个 wrapper 只在转发？这个分支不可达？ |
| ② 可读性 | 名字能读出意图吗？一个函数在做几件事？层级有没有越级混用？读者要回滚几次才能理解？ |
| ③ 注释 | 注释在复述代码，还是在解释「为什么 / 约束 / 坑」？该写没写的（IPC 约定、时序、外部依赖）补上了吗？ |
| ④ 性能 | 循环里有重复计算？响应式数据触发多余重渲染？不必要的对象/数组重建？大列表缺虚拟化？ |
| ⑤ 资源泄漏 | `addEventListener` / `setInterval` / `setTimeout` / IPC 监听 / WebSocket / 订阅，是否都有配对清理？组件卸载、路由离开、进程退出时是否释放？ |
| ⑥ 逻辑漏洞 | 边界（0、1、空、负、超大）、null/undefined、异常被吞、竞态（连点、旧请求覆盖新请求）、异步状态错乱、数据一致性 |
| ⑦ 安全/误用 | 输入有校验？权限边界清楚？这个 API 容易被用错？敏感数据是否进了日志/前端？ |

**Vue / Electron 专项信号**（命中率最高）：

- `v-for` 缺 `:key` 或用 `index` 做 key → 重渲染错位
- `watch` 监听解构后的 prop → 丢失响应性（应 `watch(() => propName, ...)`）
- 副作用 `watch` 没控制 `immediate`/`flush`，或未返回 cleanup
- `onMounted` 里开监听，没有对应 `onBeforeUnmount` / `onScopeDispose`
- 主进程 IPC handler 未校验 `event.sender`；preload `contextBridge` 暴露过多能力
- `await` 写在 `forEach` 里；忘记 `await` 的 Promise；未捕获的 reject

**错误处理 UX**（⑥「异常被吞」的延伸，重点查）：

- **就近优先**：错误要挂在**出错的位置**——输入框出错就放输入框下（Vuetify `:error-messages`）或改变字段状态，面板/卡片加载失败就在该区域内用 `<v-alert>`。**`fmsg` 浮层是退一步的兜底**，只在无法就近（瞬时操作如复制/删除、或全局背景任务）时才用。
- **失败必须让用户感知**：禁止 `.catch(() => {})` / 空 `catch {}`。可重试的失败要给重试按钮（重新拉数据/重跑初始化），瞬时操作的失败不必加。
- **禁止「失败却报成功」**：`success` 提示只能放在确认无异常的分支里（反例：`try { do(); fmsg.success() } catch {}`）。
- 文案走 `t('key')`，不硬编码；项目统一入口是全局变量 `fmsg`（`window.fmsg`，无需 import），不新建 `v-snackbar` / `useToast`。

### Step 3 — 对抗式审查（Adversarial Review）

**切换到「最坏情况」心智模型。** 不假设调用方、输入、网络、数据库、第三方服务一定正确。逐一假设它们坏掉，问代码会怎样。**每个会坏的点，都要追问「坏了之后用户感知到了吗、按上面的【错误处理 UX】闭环了吗」**——「会坏」却不反馈，就是一条发现：

| 假设会坏的环节 | 要回答的问题 |
| --- | --- |
| 调用方传参 | 传 `null` / `undefined` / 空数组 / 超大输入 / 错误类型 / 恶意构造值，会崩吗？会静默写脏数据吗？ |
| 网络请求 | 超时、500、返回半截、JSON 结构漂移、慢得离谱，loading/错误/取消态对吗？旧请求会覆盖新结果吗？ |
| 数据库 / 存储 | 返回 `null` / 重复键 / 并发写 / 损坏数据，会崩还是降级？写入失败有回滚吗？ |
| 时序 / 并发 | 疯狂连点、快速切路由、组件卸载后回调才到、双击提交，会出现重复操作或操作幽灵组件吗？ |
| 第三方依赖 | 抛错、返回 undefined、静默改 API 形状，有兜底吗？ |
| 用户行为 | 返回上一页、断网、锁屏回来、粘贴脏数据，状态会乱吗？ |

每个会崩 / 会错乱 / 会泄漏的点，记一条**发现（Finding）**。

### Step 4 — 归类发现并处置

| 级别 | 标准 | 动作 |
| --- | --- | --- |
| 🔴 Critical | 崩溃、数据错误、安全漏洞、确定性 bug、资源泄漏 | 必改 |
| 🟠 High | 高概率出错、显著性能问题、易被误用、**静默吞错 / 失败不反馈** | 改 |
| 🟡 Medium | 可读性差、轻微冗余、边界缺失但不致命 | 改（若不破坏 surgical） |
| 🟢 Nit | 风格、命名微调 | **只说不改**，除非已在改动行内 |
| ⚪ 无 | 当前实现已足够好 | 明确说明「保持不变」并讲原因 |

动作顺序遵循核心原则：**删除 > 简化 > 可读 > 保持**。

### Step 5 — 落地与验证

落地修改后**必须**跑验证，两项都过才算完成（项目硬规定）：

```bash
pnpm type-check   # 类型必须无错
pnpm lint         # 格式 + lint 必须通过
```

任一失败 → 修复 → 重跑，直到两项全绿。

提交前再跑 `detect_changes({ scope: "compare", base_ref: "main" })`，确认改动范围符合预期、没有波及无关执行流。

## 输出格式

让用户一眼看清改了什么、为什么：

```
## 审查发现
- 🔴 [符号/文件:行] 问题 → 处置
- 🟠 ...
- （🟢 Nit 只列建议，不主动改）

## 修改摘要
- 删除：...
- 简化：...
- 修复：...

## 保持不变
- [符号] 原因：已足够清晰 / 性能可接受 / 改了反而更糟

## 验证
- pnpm type-check: ✅
- pnpm lint: ✅
```

## 红线

- 不做范围外的「顺手优化」—— 只改 Step 0 确定的审查范围内的代码
- 不为「完整性」加上用户没要求的抽象、配置项、错误分支
- 不用加注释掩盖烂代码 —— 先看能不能删 / 简化
- 不在没跑 `impact` 的情况下改被多处依赖的符号
- 不静默吞错 —— 失败必须让用户感知，且**就近优先**（输入框/面板就地提示），`fmsg` 浮层只作兜底
- 不跳过 `type-check` 和 `lint` 直接交付
- 不做无谓重写：若七维度 + 对抗式都找不到实质问题，就明确说「保持不变」并讲清原因
